一、背景和目标
================================================================================

  当前 Agent (MagicArmorAgent) 与远程管理服务器的 HTTP REST 通信已经成型:
    - POST /v1/auth         上线注册
    - POST /v1/gettask      定时轮询任务
    - POST /v1/getconf →    策略/配置下发 → 存入 Agent 内存
       (POLICY_MANAGER / pattern_mgr / SHARED_USB_LIST / IP_POLICIES 等)
    - POST /v1/alertupload  批量上报告警
    - 其他 30+ 个 v1/ API

  ★ 在线 HTTP 路径已完成，本次不做任何修改。

  新增目标: 搭建本地 gRPC 服务层，使 Flutter GUI 客户端能够:
    在线时: 通过 gRPC 从 Agent 内存中读取服务器下发的策略/状态数据（只读看板）
    离线时: 通过 gRPC 替代服务器进行管控（读写，可下发任务/修改策略）


二、核心设计原则
================================================================================

  1. ★ 在线 HTTP 路径不动 —— /v1/auth、/v1/gettask、/v1/getconf 等全部保持原样

  2. 新增 gRPC 层，定位为"Agent 内存数据的查询/写入通道":

     ★ Flutter 端只调用本工程提供的 gRPC API，不需要关心 HTTP、不需要知道
       服务器地址、不区分在线离线。协议就 gRPC 一个入口。

     ★ 数据更新全被动推送，Flutter 不用轮询:

        Flutter 启动时调一次 GetXxx() 拿初始数据，之后订阅对应的流
        （SubscribeAlerts / SubscribePolicyChanges），Agent 内存数据变化时
        主动推事件，Flutter 收到事件后再调 GetXxx() 拉最新数据。

        Flutter 启动流程:
          ① GetConfig()           ← 拿初始配置
          ② GetProcessPolicy()    ← 拿初始进程策略
          ③ GetDirPolicy()        ← 拿初始目录策略
          ④ ... （所有 GetXxx 各调一次）
          ⑤ SubscribeAlerts()     ← 订阅告警流（持续推）
          ⑥ SubscribePolicyChanges() ← 订阅策略变更流（持续推）

        运行时更新流程（被动）:
          服务器 ──HTTP──→ Agent 内存变了
                              │
              SubscribePolicyChanges 推事件 "PROCESS_POLICY_CHANGED"
                              │
           Flutter 收到 → 调 GetProcessPolicy() 拉最新
           Flutter 不用轮询，完全被动

     在线时（服务器可达）:
       服务器 ──HTTP──→ Agent ─→ 策略存入内存 (POLICY_MANAGER / pattern_mgr / ...)
                                    │
       Flutter ──gRPC(只读)──────→ 只读 + 订阅流被动更新，不可修改

     离线时（服务器不可达）:
       服务器 ✗
       Flutter ──gRPC(读写)──→ 直接读写 Agent 内存中的策略/配置
                              (写操作复用现有的 handler/setter)

  3. gRPC 接口的数据格式与现有 Rust 结构体对齐，写操作直接复用现有 handler
     （handle_task / update_config_from_json / POLICY_MANAGER.set_policy_process /
       SHARED_USB_LIST.update_whitelist 等），不写两套逻辑。

  4. gRPC 框架从 virus_scan_grpc 中独立出来，新建 grpc_gateway crate
     统一管理所有 proto 定义和 gRPC Server 构建。

  5. 每个功能独立一个 proto 文件，好管理，Dart 端也能按需引入。


三、在线/离线权限模型
================================================================================

  ┌─ 在线模式（服务器可达）─┐          ┌─ 离线模式（服务器不可达）─┐
  │                         │          │                          │
  │  远程服务器 ──HTTP──→ Agent       │   Flutter GUI ──gRPC──→ Agent
  │      ↓ 下发任务           │          │      ↓ 下发任务           │
  │      ↓ 下发策略           │          │      ↓ 修改配置           │
  │      ↓ 修改配置           │          │      ↓ 更新策略           │
  │                         │          │                          │
  │  Flutter GUI ──gRPC──→ Agent      │   Agent 完全受 GUI 管控    │
  │      只看，不控           │          │                          │
  │  数据来源=服务器下发到     │          │  数据来源=GUI 本地写入     │
  │  Agent内存中的策略/配置    │          │                          │
  └─────────────────────────┘          └──────────────────────────┘

  在线时 Flutter 可以（全部 gRPC 读操作）:
    ✅ 看仪表盘/Agent 状态
    ✅ 看实时告警流
    ✅ 看进程列表、端口列表、USB 设备列表
    ✅ 看当前配置（只读）
    ✅ 看进程白/黑名单（只读）
    ✅ 看外设白/黑名单（只读）
    ✅ 看目录保护策略（只读）
    ✅ 看勒索保护策略（只读）
    ✅ 看 IP 阻断策略（只读）
    ✅ 看外联检测规则（只读）
    ✅ 看全局信任目录（只读）
    ✅ 看虚拟端口规则（只读）
    ✅ 看跳变状态、备份列表
    ✅ 病毒扫描（本地扫描，不影响服务器管控）

  在线时 Flutter 不可以（所有写操作返回 permission_denied）:
    ❌ 下发任务
    ❌ 修改配置/开关
    ❌ 更新任何策略
    ❌ 执行 IP/密码跳变
    ❌ 创建/还原备份
    ❌ 同步 NTP

  离线时 Flutter:
    ✅ 所有操作全部可用（读写）


四、离线检测 & 模式切换
================================================================================

  4.1 全局状态

      enum AgentMode {
          Online,   // 服务器可达，HTTP 通信正常
          Offline,  // 服务器不可达，gRPC 本地管控
      }

      AgentMode 由 Arc<AtomicU8> 维护，gRPC 每个 handler 入口都能读取。

  4.2 切换逻辑

      在线 → 离线:
        - /v1/auth 连续失败 N 次（连接超时/DNS 失败/拒绝连接）
        - 或 OFFLINE_MODE 配置项 = 1（手动强制离线）
        - 触发: 设置 mode = Offline，gRPC 写操作不再拒绝

      离线 → 在线:
        - 后台定时探测 /v1/auth 恢复成功
        - 触发: 设置 mode = Online，gRPC 写操作返回 permission_denied
        - 补报离线期间产生的日志/告警到服务器

  4.3 现有关键通道

      已有 host_is_offline_tx / host_is_offline_rx 通道（main.rs 中已建好但未使用）。
      需要扩展为: 写入全局 AgentMode 状态，gRPC 服务据此控制权限。

  4.4 gRPC 权限检查（每个写操作入口）

      fn require_offline(mode: &Arc<AtomicU8>) -> Result<(), Status> {
          if mode.load(Ordering::Relaxed) == AgentMode::Online as u8 {
              return Err(Status::permission_denied(
                  "在线模式下不允许此操作，请通过管理平台执行"
              ));
          }
          Ok(())
      }

六、Proto 文件逐个定义
================================================================================

  说明:
    - 每个 message 标注了对应的 Rust 结构体，字段一一对应
    - 所有消息字段的命名规则: Rust snake_case → proto snake_case（prost 自动处理）
    - optional 标注表示 Rust 侧为 Option<T>

  --------------------------------------------------------------------------
  6.0 common.proto — 通用类型
  --------------------------------------------------------------------------

    syntax = "proto3";
    package common;

    message Empty {}

    message SimpleResponse {
        bool success = 1;
        string message = 2;
    }

  6.18 policy_watch.proto — 策略变更通知流（始终可用）
  --------------------------------------------------------------------------

    解决的问题: 服务器随时可能通过 HTTP 更新策略，Flutter 不能一直轮询
              GetXxx()，需要被动通知。

    实现方式: Agent HTTP handler 更新内存数据后，往 tokio::broadcast channel
             发一个事件，gRPC 流订阅这个 channel 推给 Flutter。

    syntax = "proto3";
    package policy_watch;

    import "common.proto";

    service PolicyWatchService {
        // 订阅策略变更通知（服务端流推送）
        rpc SubscribePolicyChanges(common.Empty) returns (stream PolicyChangeEvent);
    }

    message PolicyChangeEvent {
        PolicyChangeType type = 1;
        uint64 timestamp = 2;  // 变更时间戳（毫秒）
    }

    enum PolicyChangeType {
        CONFIG_CHANGED = 0;              // → Flutter 调 GetConfig()
        PROCESS_POLICY_CHANGED = 1;      // → Flutter 调 GetProcessPolicy()
        PERIPHERAL_POLICY_CHANGED = 2;   // → Flutter 调 GetPeripheralPolicy()
        DIR_POLICY_CHANGED = 3;          // → Flutter 调 GetDirPolicy()
        EXTORT_POLICY_CHANGED = 4;       // → Flutter 调 GetExtortPolicy()
        IP_BLOCK_POLICY_CHANGED = 5;     // → Flutter 调 GetIpBlockPolicy()
        IP_BLACK_POLICY_CHANGED = 6;     // → Flutter 调 GetIpBlackPolicy()
        OUTREACH_RULES_CHANGED = 7;      // → Flutter 调 GetOutreachRules()
        TRUST_DIR_CHANGED = 8;           // → Flutter 调 GetTrustDir()
        VIRTUAL_PORT_CHANGED = 9;        // → Flutter 调 GetVirtualPort()
        JUMP_STATUS_CHANGED = 10;        // → Flutter 调 GetJumpStatus()
        BACKUP_LIST_CHANGED = 11;        // → Flutter 调 GetBackupList()
        AGENT_STATUS_CHANGED = 12;       // → Flutter 调 GetAgentStatus()
    }

    Rust 侧伪代码（在现有 HTTP handler 最后加一行）:

        // e.g. task_down_white() 最后:
        policy_change_broadcast.send(PolicyChangeType::PROCESS_POLICY_CHANGED);

    gRPC 侧伪代码:

        async fn subscribe_policy_changes(&self, _: Request<Empty>)
            -> Result<Response<...>, Status>
        {
            let mut rx = policy_change_broadcast.subscribe();
            let (tx, out_rx) = mpsc::channel(16);
            tokio::spawn(async move {
                while let Ok(change) = rx.recv().await {
                    tx.send(Ok(PolicyChangeEvent {
                        r#type: change as i32,
                        timestamp: now_millis(),
                    })).await;
                }
            });
            Ok(Response::new(ReceiverStream::new(out_rx)))
        }

八、数据同步流程（在线 + 离线）
================================================================================

  8.1 总体原则

    ★ Flutter 只调 gRPC，不关心 Agent 和服务器之间怎么通信
    ★ Flutter 不轮询任何数据，所有更新靠 gRPC 流被动推送
    ★ 在线时只读，离线时可读写

  8.2 Flutter 启动流程

    Flutter 启动
      │
      ├──① GetAgentStatus()        ← 拿仪表盘数据（一次）
      ├──② GetConfig()             ← 拿当前配置（一次，来自 NETINFO_CONFIG）
      ├──③ GetProcessPolicy()      ← 拿进程白/黑名单（一次，来自 POLICY_MANAGER）
      ├──④ GetDirPolicy()          ← 拿目录保护策略（一次，来自 pattern_mgr）
      ├──⑤ GetExtortPolicy()       ← 拿勒索保护策略（一次）
      ├──⑥ GetIpBlockPolicy()      ← 拿 IP 阻断策略（一次）
      ├──⑦ GetIpBlackPolicy()      ← 拿 IP 黑名单（一次）
      ├──⑧ GetPeripheralPolicy()   ← 拿外设策略（一次，来自 SHARED_USB_LIST）
      ├──⑨ GetOutreachRules()      ← 拿外联检测规则（一次）
      ├──⑩ GetTrustDir()           ← 拿信任目录（一次）
      ├──⑪ GetVirtualPort()        ← 拿虚拟端口规则（一次）
      ├──⑫ GetJumpStatus()         ← 拿跳变状态（一次）
      ├──⑬ GetBackupList()         ← 拿备份列表（一次）
      │
      ├──⑭ SubscribeAlerts()       ← 订阅告警流（持续）
      └──⑮ SubscribePolicyChanges() ← 订阅策略变更流（持续）

  8.3 在线模式运行时更新（被动推送）

    服务器任何时候都可能通过 HTTP 更新策略，Agent 更新内存后立即推送:

    服务器 ──HTTP──→ Agent ─→ POLICY_MANAGER.lock() = 新数据
                        │
                        │  policy_change_broadcast.send(PROCESS_POLICY_CHANGED)
                        │
                        ↓
              SubscribePolicyChanges 流推: {type: PROCESS_POLICY_CHANGED, timestamp: ...}
                        │
                        ↓
              Flutter 收到 → 调 GetProcessPolicy() 拉最新数据 → 刷新 UI
              Flutter 不轮询，完全被动

    所有策略类型的更新路径:

    服务器 HTTP           Agent 内存更新              gRPC 推送事件              Flutter 刷新
    ─────────────────────────────────────────────────────────────────────────────────
    POST /v1/getconf    → NETINFO_CONFIG.lock()    → CONFIG_CHANGED          → GetConfig()
    POST /v1/getprocwl  → POLICY_MANAGER.lock()    → PROCESS_POLICY_CHANGED  → GetProcessPolicy()
    POST /v1/getprocbl  → POLICY_MANAGER.lock()    → PROCESS_POLICY_CHANGED  → GetProcessPolicy()
    POST /v1/getdirpolicy → pattern_mgr.lock()     → DIR_POLICY_CHANGED      → GetDirPolicy()
    POST /v1/getprotect → pattern_mgr.lock()       → EXTORT_POLICY_CHANGED   → GetExtortPolicy()
    POST /v1/getPlugging → IP_POLICIES             → IP_BLOCK_POLICY_CHANGED → GetIpBlockPolicy()
    POST /v1/getipblacklist → IP_POLICIES          → IP_BLACK_POLICY_CHANGED → GetIpBlackPolicy()
    ...白名单              → SHARED_USB_LIST.lock() → PERIPHERAL_POLICY_CHANGED → GetPeripheralPolicy()
    ...外联检测规则         → outreach_rules         → OUTREACH_RULES_CHANGED  → GetOutreachRules()
    ...信任目录            → PROCESS_PATTERN_RULES  → TRUST_DIR_CHANGED       → GetTrustDir()
    ...虚拟端口            → /proc/osec/net_rules   → VIRTUAL_PORT_CHANGED    → GetVirtualPort()
    ...IP跳变/密码跳变      → jump状态变化           → JUMP_STATUS_CHANGED     → GetJumpStatus()

  8.4 离线模式

    服务器不可达，无 HTTP 推送。
    Flutter 通过 gRPC 写操作直接修改 Agent 内存 → Agent 自己更新后
    同样发 policy_change_broadcast，其他订阅者也能收到。

  8.5 结论

    在线模式下:
      - 读操作从内存获取数据，零额外开销
      - 数据变更通过 gRPC 流被动推送，Flutter 不轮询
      - HTTP 路径完全不动，只在原有 handler 末尾加一行 broadcast.send()

    离线模式下:
      - 写操作直接修改同一份内存数据
      - 同样走 broadcast 通知，逻辑一致


九、AgentDataHub — 统一数据访问层
================================================================================

  9.1 问题

    当前 Agent 的策略/配置数据分散在各 crate 的全局变量中:

      POLICY_MANAGER        ← process_mgr crate     — Mutex<ProcessPolicyManager>
      NETINFO_CONFIG        ← config crate          — Mutex<NetInfoConfig>
      SHARED_USB_LIST       ← udisk crate           — Mutex<UsbListManager>
      pattern_mgr           ← pattern crate         — Mutex<PatternRulesMgr>
      IP_POLICIES           ← netblock crate        — RwLock<HashMap>
      outreach_rules        ← task crate            — RwLock<Vec<OutreachDetectRule>>
      PROCESS_PATTERN_RULES ← pattern crate         — Mutex<ProcessPatternRulesMgr>
      ...

    问题:
      - gRPC handler 要读策略，得各自 import 不同 crate 的全局变量
      - 变更通知要每个 HTTP handler 各自发，散落各处容易遗漏
      - 写操作要各自加锁、修改、发通知，逻辑重复

  9.2 三种方案对比

    |                        | 各自独立全局变量(现状) | 一个大结构体全包    | AgentDataHub(推荐) |
    |------------------------|----------------------|---------------------|--------------------|
    | 锁粒度                  | ✅ 细，互不干扰       | ❌ 粗，一锁全堵      | ✅ 细，独立锁       |
    | 对现有HTTP代码影响        | —                    | ❌ 全改              | ✅ 完全不动          |
    | gRPC handler 依赖        | ❌ 各自 import 一堆   | ✅ 只依赖 Arc\<State\> | ✅ 只依赖 Arc\<Hub\> |
    | 变更通知统一入口           | ❌ 各自为政          | ✅ 统一              | ✅ 统一              |
    | 代码发现性               | ❌ 散落各处          | ✅ 一个文件看全貌     | ✅ 一个 hub 看全貌   |
    | 测试 mock               | ❌ 各自 mock         | ✅ 一个 mock          | ✅ 一个 mock         |

  9.3 方案：AgentDataHub

    不动现有全局变量，只在上面加一个薄的统一访问层，gRPC handler 全部通过 Hub 读写。

    位置: crates/agent_local_svc/src/data_hub.rs

  9.4 伪代码

    pub struct AgentDataHub {
        change_tx: broadcast::Sender<PolicyChangeType>,
    }

    impl AgentDataHub {
        pub fn new() -> Self {
            let (change_tx, _) = broadcast::channel(64);
            Self { change_tx }
        }

        /// 通知所有 gRPC 订阅者：某类策略已变更
        pub fn notify(&self, change: PolicyChangeType) {
            let _ = self.change_tx.send(change);
        }

        /// gRPC SubscribePolicyChanges 用
        pub fn subscribe_changes(&self) -> broadcast::Receiver<PolicyChangeType> {
            self.change_tx.subscribe()
        }

        // ── 读示例 ──

        pub fn get_config(&self) -> NetInfoConfig {
            NETINFO_CONFIG.lock().unwrap().clone()
        }

        pub fn get_process_policy(&self, is_white: bool) -> ProcessPolicy {
            let mgr = POLICY_MANAGER.lock().unwrap();
            let hashes = if is_white { mgr.get_white_list() } else { mgr.get_black_list() };
            ProcessPolicy { hash_list: hashes, is_white }
        }

        // ── 写示例 ──

        pub fn update_process_policy(&self, hash_list: &[String], is_white: bool) -> Result<(), String> {
            POLICY_MANAGER.lock().unwrap().set_policy_process(hash_list, is_white);
            self.notify(PolicyChangeType::PROCESS_POLICY_CHANGED);
            Ok(())
        }

        pub fn update_config(&self, cfg_data: &ConfigData) -> Result<(), String> {
            // 复用现有 update_config_from_json 的核心逻辑
            let mut guard = NETINFO_CONFIG.lock().unwrap();
            // ... 应用配置变更到 *guard ...
            guard.to_ini(&format!("{}/net_info.ini", guard.app_path))?;
            self.notify(PolicyChangeType::CONFIG_CHANGED);
            Ok(())
        }
    }

  9.5 HTTP handler 改动（极小）

    在现有 HTTP handler 末尾加一行 notify() 即可接入 gRPC 通知。改动量很小:

      // task_fetcher.rs — task_down_white()
      async fn task_down_white(&self, ...) -> Result<(), String> {
          // ... 现有代码：拉取、解析、更新 POLICY_MANAGER ...
          // ★ 新增一行:
          self.data_hub.notify(PolicyChangeType::PROCESS_POLICY_CHANGED);
          Ok(())
      }

    其他 handler 同理，每个只在末尾加一行 notify()。

  9.6 gRPC handler 用法

    // agent_local_svc/src/config_impl.rs
    pub struct ConfigServiceImpl {
        data_hub: Arc<AgentDataHub>,
        agent_mode: Arc<AtomicU8>,
    }

    #[tonic::async_trait]
    impl ConfigService for ConfigServiceImpl {
        async fn get_config(&self, _: Request<Empty>)
            -> Result<Response<ConfigData>, Status>
        {
            let cfg = self.data_hub.get_config();
            Ok(Response::new(cfg.to_proto()))
        }

        async fn update_config(&self, req: Request<ConfigData>)
            -> Result<Response<ConfigResponse>, Status>
        {
            require_offline(&self.agent_mode)?;       // 在线模式拒绝
            let cfg = req.into_inner();
            self.data_hub.update_config(&cfg)
                .map(|_| Response::new(ConfigResponse { success: true, ... }))
                .map_err(|e| Status::internal(e))
        }
    }

  阶段5: main.rs 装配
    - 创建 AgentDataHub（Arc）注入所有 gRPC handler
    - 在线: 注册所有 Get*(读) + SubscribeAlerts + SubscribePolicyChanges + VirusScan
    - 离线: 注册全部读写 service
    - 监听地址: 在线 127.0.0.1:50051，离线可配 0.0.0.0

  阶段6: Flutter GUI 对接
    - 基于 grpc_gateway 的 proto 生成 Dart 客户端代码
    - 替换模拟数据为真实 gRPC 调用
    - 在线/离线 UI 状态区分
