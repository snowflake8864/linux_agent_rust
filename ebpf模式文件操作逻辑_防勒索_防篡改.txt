eBPF 模式文件操作逻辑（防勒索 / 防篡改）
========================================

说明
----
本文只描述 eBPF 模式（backend_mode=ebpf）下 file_agent 的文件操作管控逻辑，
包括防勒索（lesuo / extortion）和防篡改（tamper / dir policy）。
驱动模式不在本文范围。

涉及代码：
- ebpf-probes/bpf/file_agent.bpf.c      BPF 侧规则表、匹配、拦截、事件
- crates/ebpf_backend/src/dpi_parser.rs 策略文本解析
- crates/ebpf_backend/src/lib.rs        BPF map 下发、路径补全、MD5、事件上报
- crates/ebpf_backend/src/types.rs      BPF map/事件结构，必须与 C 结构一致
- crates/pattern/src/pattern_rules_mgr.rs 策略文本生成
- crates/task/src/task_fetcher.rs       配置开关同步
- crates/main/src/main.rs               加载 file_agent、启动参数


一、开关与模式
--------------
运行时开关来自服务器配置 / net_info.ini：

1. 防篡改
   - FILE_SWITCH   -> feature_switches[0]  (0=暂停, 1=启用)
   - FILE_PROTECT  -> global_modes[0]      (0=监控, 1=拦截)
   对应 task_fetcher::sync_switches -> EbpfBackend::sync_runtime_switches。

2. 防勒索
   - EXTORTION_SWITCH  -> extort_switches[0] (0=暂停, 1=启用)
   - EXTORTION_PROTECT -> extort_switches[1] (0=监控, 1=拦截)
   对应 EbpfBackend::set_extort_switches，独立于 FILE_SWITCH/FILE_PROTECT。
   即使 FILE_SWITCH=0，只要 EXTORTION_SWITCH=1，勒索规则仍可工作；
   只要 EXTORTION_SWITCH/PROTECT 有一个开启，main 也会加载 file_agent。

3. 自保护
   - self_protect_switch -> self_protect_dirs + protected_pids
   - 自保护独立于 file_switch，也不走 dir_policies（见第六节）。

模式语义：
- MONITOR(监控)：匹配后只发事件，不返回 -EPERM。
- PROTECT(拦截)：匹配且 action=DENY 时返回 -EPERM，操作被拒绝。
- agent 自身进程始终通过 is_agent_process() 放行，避免代理写配置被自己拦截。


二、BPF map
-----------
file_agent.bpf.c 主要 map：

1. feature_switches      ARRAY[3]  0=文件, 1=进程, 2=网络
2. global_modes          ARRAY[3]  0=文件模式, 1=进程模式, 2=网络模式
3. dir_policies          HASH
   key   = struct dir_key { u64 dev; u64 inode; }   父目录 inode
   value = struct dir_policy {
       u8 ops_mask;       // READ/WRITE/CREATE/DELETE/RENAME 位图
       u8 action;         // 0=ALLOW, 1=DENY
       u8 mode;           // 0=继承全局, 1=监控, 2=拦截
       u8 recursive;      // 1=该目录策略需要覆盖子目录
       u8 filter_type;    // 0=无, 1=include 后缀, 2=exclude 后缀, 3=精确文件名
       u8 suffix_count;
       u8 reserved[2];
       u8 suffixes[8][8]; // 小后缀（历史上最多 8 个，每个 8 字节）
       u8 exact_filename[32];
   }
   说明：当前 eBPF 实现主要使用 include/exclude 后缀；exact_filename 结构存在，
        但策略解析侧尚未生成 filter_type=3 的规则。

3.1 file_policies        HASH
   key   = struct dir_key { u64 dev; u64 inode; }  具体文件自身 inode
   value = struct dir_policy                        与 dir_policies 相同
   用途：防篡改“具体文件”策略。只对策略下发时已经存在的普通文件生效。
   说明：BPF 在 file_open/inode_unlink/inode_rename 中用目标文件 inode 查表，
        不查父目录；命中后按 ops_mask/action/mode 拦截或监控。
        文件策略的 filter_type/suffix 会被清 0（按文件对象精确命中）。

4. extort_suffixes       HASH
   key   = char[16]  文件最后一个 '.' 之后的后缀（右侧补 0）
   value = u32       规则索引（同时是 extort_trusted 的位号）
   例：name=exiportInfo_0,key=.docx -> key "docx"

5. extort_dirs           HASH
   key   = struct dir_key { dev, inode }  规则目录或其子目录 inode
   value = u32        规则索引（同上）
   用途：目录型勒索规则（驱动 action=0 include dir）。

6. extort_switches       ARRAY[2]
   [0] = EXTORTION_SWITCH
   [1] = EXTORTION_PROTECT

7. extort_trusted        HASH
   key   = struct extort_proc_key { u32 dev; u64 inode; }  进程可执行文件 inode
   value = u32 mask    允许的勒索规则索引位图
   语义：当前进程 exe inode 命中该表且 mask 含当前规则位 -> 放行该规则。

7.1 tamper_trusted      HASH
   key   = struct tamper_proc_key { u32 dev; u64 inode; } 进程可执行文件 inode
   value = u64 mask    允许的防篡改 TPNC 规则号位图（bit = rule_id-1）
   语义：dir_policy.trust_rule = TPNC 规则号；BPF 用当前进程 exe inode 查表，
        命中对应 bit 则视为可信进程，直接放行该防篡改策略（不拦截、不告警）。

8. self_protect_dirs     HASH
   key   = dir_key
   value = self_protect_rule { whole_dir, prefix_count, prefixes[2][16] }
   自保护专用，和 dir_policies 独立。

9. path_scratch          PERCPU_ARRAY  scratch 路径/文件名/argv/cwd
10. event_ringbuf        RINGBUF       文件事件
11. agent_pids           ARRAY         agent 自身 PID


三、策略文本 -> BPF map
-----------------------
PatternRulesMgr 生成 DPI 文本，EbpfBackend 解析后写 BPF map。

1. 防篡改目录策略 set_protect_dir
   每个策略生成：
   - pattern: name=ProtectDir_<i>,type=2,key=<dir>,depth=<len>,case_offset=1
     - is_extend=0 时额外写 isnot_extend=1
   - include_file（如 "txt|doc"）生成链式规则：
     target=protectIncFileExe_<i>,pattern=ProtectDir_<i>>protectIncFileExe_<i>_<j>,
     action=3,protect_rw=<bits>,rule_idx=<i>,type=2
   - file_ext（排除后缀）生成 action=2 的链式规则
   - 无 include/exclude 时：
     target=ProtectDir_<i>,pattern=ProtectDir_<i>,rule_idx=<i>,protect_rw=<bits>,type=2
   - is_white（目录白名单）生成 target=protectExcludeDir,... action=1
   - white_hash（可信进程 hash）生成 true_process 行：hash,rule_id,88
   - TPNC=<rule_id> 指向 true_process 行

   dpi_parser::match_patterns_to_rules:
   - 解析 pattern/rule 文本；
   - 只处理 key 为目录路径（不以 '.' 开头）的规则；
   - resolve_dir_to_key(key) -> (dev,inode)；
   - compute_ops_mask 把 protect_rw 位映射为 ops_mask：
       bit0 read   -> OP_READ
       bit1 write  -> OP_WRITE
       bit2 delete -> OP_DELETE
       bit3 rename -> OP_RENAME
       bit4 create -> OP_CREATE
     注意：protect_rw=15 只含 read/write/delete/rename，不含 create。
   - include/exclude 后缀合并到 dir_policy.suffixes；
   - recursive = isnot_extend ? 0 : 1；
   - 同一 (dev,inode) 的多条规则合并：DENY 优先，ops OR，后缀合并。

   下发时的文件/目录区分（commit_dpi_to_bpf）：
   - stat(entry.path).is_file() == true  -> 写 file_policies（具体文件，不递归、不做后缀过滤）
   - 否则                                -> 写 dir_policies（目录策略，可按 recursive 展开子目录）
   - 具体文件策略同时缓存其父目录路径，便于 delete/rename 事件补全全路径。

2. 防勒索策略 set_exiport_dir
   - typ==1（文件后缀）：
       pattern: name=exiportInfo_<i>,key=.<file_type>,offset=-(len+1)
       rule:    target=...,pattern=...,action=3,type=1[,TPNC=<id>]
   - typ!=1（目录）：
       pattern: name=exiportInfo_<i>,key=<file_type>,depth=<len>,case_offset=1
       rule:    target=...,pattern=...,type=1[,TPNC=<id>]
   - 有 map_comm（hash->进程名）时生成 true_process 行：
       hash,<rule_id>,99
     TPNC=<rule_id> 引用。

   dpi_parser:
   - parse_extort_rules: 解析 type=1 + action=3 + key 以 '.' 开头的规则，
     得到后缀列表；去重；规则索引 0..n-1。
   - parse_extort_dir_rules: 解析 type=1 + action=0 + key 为绝对路径的规则，
     得到目录型勒索规则；规则索引接在后缀规则之后。
   - parse_true_processes: 解析 true_process 文本 `hash,rule_id,rule_type`，
     只取 rule_type=99 作为勒索可信进程。

3. 信任进程下发（勒索）
   commit_extort_bpf:
   - 后缀写 extort_suffixes: key=后缀，value=规则索引；
   - 目录型写 extort_dirs，并递归展开规则目录下已存在的子目录；
   - true_process 行按 rule_id 找到对应规则索引，形成 hash -> mask 位图；
   - 用 md5_map / md5_inode_cache 把 hash 翻译成 (dev,inode)，
     写 extort_trusted[key] = mask；
   - 未解析的 hash 保存在 extort_trust_hashes，后续进程被发现时补写；
   - 同一 (dev,inode) 来自多个 hash 时 mask 按位 OR，避免覆盖。

3.2 信任进程下发（防篡改 TPNC/88）
   - set_protect_dir 有 white_hash 时生成 true_process 行：hash,rule_id,88，
     规则行携带 TPNC=<rule_id>；
   - dpi_parser 把 TPNC 解析成 dir_policy.trust_rule（1..64）；
   - commit_tamper_trust_bpf：
       * 只处理 rule_type=88；
       * 形成 hash -> u64 位图（1 << (rule_id-1)）；
       * 用 md5_map / md5_inode_cache 把 hash 翻译成 (dev,inode)，
         写 tamper_trusted[key] = mask（同 key 多 hash 按位 OR）；
       * 未解析 hash 挂起，进程被扫描/发现/文件事件命中时补写。
   - 用户态只负责 hash -> inode 和写 map；是否放行由 BPF 判断。

4. 防篡改递归
   - BPF 只查直接父目录 inode，不做祖先链循环（避免 verifier 超限）。
   - 用户态在 commit 时对 recursive=1 的策略目录递归遍历子目录，
     把同一个 dir_policy 写到每个子目录 inode。
   - 只覆盖策略下发时已经存在的子目录；之后新建的子目录是否覆盖取决于
     是否有额外事件/机制（当前没有内核 mkdir 后自动补写，属于已知限制）。


四、运行时匹配逻辑（BPF）
-------------------------
所有文件钩子入口先判断：
  if (is_agent_process()) return 0;

1. file_open（lsm.s/file_open）
   适用于 open/read/write/create(path open O_CREAT) 等。
   步骤：
   1) 从 file->f_flags 解析 op_type：
      O_RDONLY -> OP_READ
      O_WRONLY -> OP_WRITE
      O_RDWR   -> OP_READ|OP_WRITE
      实际创建（f_mode & FMODE_CREATED）时 op_type 改为 OP_CREATE。
   2) 取 dentry、父目录 inode，生成 dir_key。
   3) 取叶子文件名。
   4) 生成全路径：
      bpf_d_path(&file->f_path, scratch->full, 512)
      失败则fullpath=0，后续用父目录+叶子让应用层补。
   5) 自保护检查：写操作命中 self_protect_dirs -> 拦截并发 EVENT_SELF_PROTECT。
   6) 勒索检查 extort_check：
      - 如果文件不是目录，按最后一个 '.' 后的后缀查 extort_suffixes；
      - 如果父目录 inode 在 extort_dirs，命中目录型勒索；
      - 如果目标 inode 本身在 extort_dirs，命中所属目录规则；
      - 命中后查 extort_trusted[当前进程 exe inode] 的 mask，含该规则位则放行；
      - EXTORTION_PROTECT=1 -> 发 EVENT_EXTORT(blocked=1) 并返回 -EPERM；
      - EXTORTION_PROTECT=0 -> 发 EVENT_EXTORT(blocked=0) 继续。
      - 注意：勒索检查对读打开也生效，不只写。
   7) 如果 feature_switches[0]=0，跳过防篡改。
   7.1) 具体文件策略：用目标文件自身 inode 查 file_policies；
        命中且 ops_mask 包含当前 op_type 时：
        - is_tamper_trusted(fp) -> 跳过该文件策略，继续父目录策略；
        - 否则按 mode/action 发事件并拦截/放行。
   8) 用父目录 dir_key 查 dir_policies。
   9) 如果 ops_mask 不含当前 op_type -> 放行。
   9.1) is_tamper_trusted(policy)：当前进程 exe inode 在 tamper_trusted 中
        且 mask 含 trust_rule 位 -> 直接放行（不告警、不拦截）。
   10) check_exact_match / check_suffix 过滤叶子名。
   11) effective_mode = resolve_mode(policy.mode, FEATURE_FILE)。
   12) PROTECT + action=DENY -> 发 EVENT_FILE 拦截并返回 -EPERM；
       否则发 EVENT_FILE 监控。

2. inode_create（lsm.s/inode_create）
   - 自保护写检查；
   - 防勒索已移出 create（避免和 file_open 重复发叶子名事件）；
   - 具体文件策略不参与 create（文件已存在才会下发）；
   - feature_switches[0] 关闭则放行；
   - 父目录 dir_policies 检查 OP_CREATE；
   - PROTECT + DENY -> -EPERM（不发事件；事件由后续 file_open 全路径上报）。

3. inode_unlink（lsm.s/inode_unlink）
   - 自保护检查；
   - 勒索检查（后缀/目录型）；
   - 具体文件策略：目标 inode 在 file_policies 且 ops 含 DELETE，
     且非可信进程 -> 拦截/上报；
   - 父目录 dir_policies 的 OP_DELETE，且 is_tamper_trusted 为假才拦截；
   - PROTECT + DENY -> -EPERM；
   - 告警事件：当前版本在 inode_unlink 中不再直接发 EVENT_FILE（避免重复），
     delete 的全路径事件依赖 file_open/应用层补全策略；
     若需要 delete 独立全路径事件，需要额外 path 钩子/扩展（见第九节）。

4. inode_rename（lsm.s/inode_rename）
   - 自保护检查源/目标；
   - feature 关闭则放行；
   - 源/目标文件自身 inode 查 file_policies 的 OP_RENAME（可信进程跳过该策略）；
   - 源父目录、目标父目录分别查 dir_policies 的 OP_RENAME（可信进程跳过）；
   - 任一 PROTECT+DENY -> -EPERM；
   - 目录型勒索 rename 由单独的 enforce_extort_inode_rename 程序处理；
     后缀型勒索 rename 仍未放入主 rename（避免 verifier 超限）。

5. inode_mkdir（lsm/inode_mkdir，非 sleepable）
   - 自保护检查；
   - 目录型勒索：父目录 inode 在 extort_dirs -> 发 EVENT_EXTORT，protect 模式拦截；
   - feature 关闭则放行；
   - 父目录 dir_policies 的 OP_CREATE（可信进程跳过）；
   - PROTECT+DENY -> -EPERM；
   - 该钩子非 sleepable，不能调 bpf_d_path，事件用 nocwd 发送（不捕获 cwd），
     全路径依赖应用层父目录缓存/参数补全。

6. inode_rmdir（lsm.s/inode_rmdir）
   - 自保护检查；
   - 目录型勒索：父目录/目标目录 inode 在 extort_dirs -> EVENT_EXTORT；
   - 父目录 dir_policies 的 OP_DELETE（可信进程跳过）-> 拦截/事件。

6. 自保护 self_protect_dirs
   - 从 dentry 向上最多 8 层查 self_protect_dirs；
   - whole_dir=1：目录子树全部拦截；
   - whole_dir=0：只对直接父目录(第0层)的文件名前缀匹配，如 osec. / agent_manager.
   - 写操作才检查；独立于 file_switch。

7. 事件结构 unified_event / FileEvent
   字段：
     type, op_type, blocked
     pid, uid
     parent_dev, parent_ino     父目录 inode（应用层补路径）
     exe_dev, exe_ino           当前进程 exe inode（进程 MD5）
     comm[16]
     path[256]                  全路径或叶子名
     cmdline[256]               事件发生时 BPF 拷贝的 argv
     cwd[256]                   事件发生时 BPF 拷贝的 cwd 全路径
   event.type:
     1=EVENT_FILE, 4=EVENT_SELF_PROTECT, 5=EVENT_EXTORT


五、应用层全路径补全
--------------------
目标：BPF 没给全路径时（delete/rename/mkdir/rmdir、bpf_d_path 失败），
应用层尽量补出全路径。

1. dir_path_cache: (dev,inode) -> path
   来源：
   - 防篡改策略目录及其递归展开子目录；
   - 勒索目录型规则的规则目录及子目录；
   - 任意带全路径的事件（file_open）发生后，缓存其所有祖先目录；
   - 事件处理时从 /proc/<pid>/cwd、/proc/<pid>/fd 补。

2. 事件处理顺序（resolve_event_full_path）
   a) path 以 '/' 开头 -> 已是全路径；缓存其祖先目录；
   b) 只有叶子名：
      - 查 dir_path_cache[parent_dev,parent_ino]；
      - 用事件中 BPF 捕获的 cmdline 解析：
          * argv 中的绝对路径；
          * argv 中的相对路径 -> 拼事件中的 cwd；
          * 必须满足 file_name == 叶子名 且 参数父目录 inode == 事件父目录；
      - 查 /proc/<pid>/cwd 及其祖先目录；
      - 查 /proc/<pid>/fd 目标及其祖先目录；
      - 都不行 -> 保持叶子名。

3. 为什么需要 BPF 捕获 cmdline/cwd
   - rm 等进程生命周期很短，用户态再去读 /proc/<pid>/cmdline 或 cwd 时
     进程常常已经退出，导致相对路径无法解析；
   - 现在在 send_monitor_event 中直接读取当前 task 的 argv 和 cwd 并写进
     事件，应用层不再依赖进程是否存活。

4. 进程 MD5
   - 不取被操作文件的 MD5，而是取操作进程 exe 的 MD5；
   - 优先 inode_md5_map[(exe_dev,exe_ino)]；
   - 没有则读 /proc/<pid>/exe 计算 MD5（进程已退出时可能失败，故优先 BPF inode）；
   - 上报字段 md5 使用该进程 MD5。


六、防勒索（lesuo）语义总结
--------------------------
- 后缀规则：文件在任意目录，扩展名命中 extort_suffixes 即命中。
- 目录规则：文件/子目录/操作对象的父目录在 extort_dirs，或目标 inode 在 extort_dirs。
- 信任进程：按规则位图 mask 放行，支持：
  * 一条规则多个 hash（多个 (dev,inode)）；
  * 一个 hash 被多条规则信任（mask OR）；
  * 未解析 hash 挂起，进程被发现后补写。
- 模式：
  * EXTORTION_PROTECT=0 -> 只监控上报；
  * EXTORTION_PROTECT=1 -> 拦截 (-EPERM)。
- 事件 n_type：拦截 3201，监控 3202。
- 支持的覆盖对象：
  * file_open: read/write/create
  * inode_unlink: delete（拦截）
  * inode_rename: rename（目录策略 + 目录型勒索；后缀勒索未检查）
  * inode_mkdir: mkdir（目录型勒索 + dir_policies）
  * inode_rmdir: rmdir（目录型勒索 + dir_policies）
- 限制：
  * 后缀只取最后一个 '.' 之后的内容，不支持 tar.gz 这类多级后缀
    （除非上层把策略拆成 gz 等单级后缀）。
  * 后缀表为 hash，不是 LPM；单级后缀 O(1)。
  * 规则总数/信任位图 32 位，后缀+目录规则合计超过 32 条会截断。
  * rename 的后缀勒索检查当前未生效。
  * 目录型勒索已覆盖 mkdir/rmdir/rename（rename 由独立轻量程序处理）。
  * 规则目录下新创建的子目录不会自动写入 extort_dirs（依赖重新下发策略展开）。


七、防篡改（dir policy）语义总结
--------------------------------
- 单位：目录策略（dir_policies），key 为父目录 inode。
- protect_rw -> ops_mask：
  * 0 -> 默认所有操作
  * bit0 read / bit1 write / bit2 delete / bit3 rename / bit4 create
- include_file（action=3）：只保护指定后缀；
- file_ext（action=2）：排除指定后缀；
- 目录白名单 is_white（action=1）：生成 ALLOW 目录策略；
- 递归 is_extend=1：用户态预展开子目录，BPF 仍 O(1) 查直接父目录；
- 模式：FILE_PROTECT=0 监控，FILE_PROTECT=1 拦截；
- 事件 n_type：文件 3001-3005（监控）/3101-3105（拦截）。

已知限制：
- 新创建的子目录不会自动继承（除非重新下发策略触发展开）。
- 白名单目录和递归展开可能互相覆盖：递归展开会把 DENY 写到子目录，
  如果白名单目录也在其中，最终 key 以最后写入/合并结果为准，存在风险。
- white_hash（防篡改可信进程，TPNC/88）已在 BPF 生效：
  用户态把 hash 翻译成 (dev,inode) 写 tamper_trusted，
  BPF 用 dir_policy.trust_rule 查当前进程 exe inode 的 mask，命中则放行。
- 具体文件保护：支持“已存在的普通文件”（file_policies，见第八节）。


八、防篡改对“具体文件”的支持情况
--------------------------------
结论：当前 eBPF 模式支持对“已经存在的普通文件”的防篡改保护。

实现方式：
1. 策略里的 dir 字段既可以是目录，也可以是具体文件。
2. dpi_parser 解析策略时仍解析成 (dev,inode)；
   commit_dpi_to_bpf 对每条策略做 stat(entry.path)：
   - 普通文件 -> 写 file_policies[文件 inode]；
   - 目录     -> 写 dir_policies[目录 inode]，可递归展开。
3. BPF 运行时：
   - file_open：用目标文件自身 inode 查 file_policies，ops_mask 命中则按
     mode/action 发事件并拦截/放行；
   - inode_unlink：用 dentry->d_inode 查 file_policies，匹配 OP_DELETE；
   - inode_rename：源/目标文件 inode 分别查 file_policies，匹配 OP_RENAME；
   - file_open/rename/unlink 事件全路径优先用 bpf_d_path/父目录缓存/argv+cwd 补全。
4. 文件策略不递归、不做 include/exclude 后缀过滤（按文件对象精确命中）。
5. 文件不存在时无法下发：resolve_dir_to_key/stat 失败，策略不会生效；
   文件删除后重建（inode 变化）需要重新下发策略。

驱动模式：
- 驱动按完整路径字符串匹配，文件路径完全相等时也能命中；
- eBPF 现在通过 file_policies 按文件 inode 实现，效果等价（限已存在文件）。


九、当前已知缺口 / 待办
----------------------
1. 防篡改具体文件支持：已实现（file_policies，仅已存在文件；重建后需重下发）。
3. 勒索 rename 后缀检查：为过 verifier 从主 inode_rename 移除，目录型勒索已由独立程序覆盖。
4. 勒索 mkdir/rmdir：已覆盖目录型规则；新建子目录不会自动加入 extort_dirs。
5. 防篡改新子目录自动继承：依赖用户态预展开，运行期新建子目录不自动补。
6. 多级后缀（tar.gz）不支持。
7. 规则位图 32 位上限。
8. delete/rename 全路径依赖应用层补全，冷目录仍可能只剩叶子名；
   已加入 BPF argv/cwd 捕获 + 用户态祖先缓存，覆盖 rm/mv 常见场景。
9. path LSM 钩子不是 sleepable，不能 bpf_d_path；手写 dentry 路径构建
   当前会导致 verifier 超 100 万指令，未采用。


十、验证方法
------------
1. 防勒索后缀（监控模式）
   - EXTORTION_SWITCH=1, EXTORTION_PROTECT=0
   - 在任意目录 touch/写入 .txt/.html
   - backend.log 应出现：
     勒索防护命中: path=<全路径> comm=<进程> blocked=false
     文件告警: n_type=3202 ... proc_md5=<进程MD5>
   - 不应出现同一次操作的重复叶子名事件。

2. 防勒索拦截
   - EXTORTION_PROTECT=1
   - 写入受保护后缀应失败（Permission denied），日志 blocked=true、n_type=3201。

3. 防篡改目录
   - FILE_SWITCH=1, FILE_PROTECT=1
   - 在策略目录（及 is_extend=1 的子目录）修改/删除受保护后缀文件
   - 应拦截；监控模式下 n_type=3001-3005、拦截模式 3101-3105。

4. 具体文件
   - 策略 dir 指向已存在文件，下发后日志出现：
     [EbpfBackend] 具体文件策略: dev=... inode=... ops=0x.. action=1
     DPI commit: N 条具体文件策略
   - 读/写/删/改名该文件，应出现文件告警，path 为全路径；
     protect_rw 决定哪类操作命中（例如 protect_rw=13 不含 write）。

5. 信任进程
   - 勒索：extort_trusted，按 rule_type=99；
   - 防篡改：tamper_trusted，按 rule_type=88，dir_policy.trust_rule 位；
   - 策略里一个规则配置多个 hash，或多个规则共用同一 hash；
   - 日志应看到多个 trusted 写入，mask 正确合并；
   - 用可信进程操作不受保护（防篡改不告警/不拦截），
     用非可信进程操作会命中。
